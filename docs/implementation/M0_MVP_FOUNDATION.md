# 第一步：建立 MVP 的事务反馈环

> 阶段：M0（已完成）
>
> 目标：用一个真实数据库测试，证明业务数据和 Outbox 事件能够一起提交、一起回滚。

## 这一步做什么

先搭建最小 Maven 工程，引入 MySQL 8.0 Testcontainers，创建 `reliable_event_outbox` 表，并写一条事务回滚集成测试。

测试只验证一个关键行为：业务事务主动回滚后，业务数据和 Outbox 事件都不存在。

M0 是 MVP 的地基；完成 M0 后，M1 再补上 `publish`、后台扫描、Fake 发送和成功状态更新，形成完整的最小发布闭环。

## 为什么先做这个

ReliableEvent 最核心的承诺不是“能发送消息”，而是“业务数据和待发送事件不会发生本地事务上的分离”。如果这一点没有被真实测试证明，后面的扫描、重试、租约和 RocketMQ 接入都建立在未经验证的前提上。

因此第一步先验证最小风险点：同一个 Spring 事务、同一个数据源、同一个数据库连接是否真正覆盖业务写入和 Outbox 写入。

## 做完有什么用

- 得到项目第一条可自动重复执行的可靠性证据，而不只是设计说明。
- 尽早发现事务传播、数据源或建表脚本配置错误。
- 建立后续功能共同使用的 MySQL 集成测试环境。
- 以后修改持久化代码时，可以立即发现是否破坏了原子性。
- 为 M1 的最小发布闭环提供一张真实、可查询的 Outbox 表。

## 我是怎么考虑的

这一步刻意保持小范围：

- 使用真实 MySQL 8.0 容器，不使用 H2 模拟，因为项目依赖 MySQL 的事务行为、JSON 字段和时间精度。
- 暂时只保留满足测试所需的模块，不提前创建全部计划模块，避免空架构增加理解成本。
- 暂时使用测试夹具代替 RocketMQ，因为此时要验证的是数据库原子性，不是消息中间件连通性。
- 先测试外部可观察行为，不急着完善所有领域对象和扩展接口。
- 暂不处理并发抢占、重试、租约和死信；这些能力分别属于 M2 和 M3。

判断标准很简单：在干净环境执行测试时，事务提交会同时留下两类记录，事务回滚不会留下孤立的 Outbox 事件。满足这一点，才进入 M1。
