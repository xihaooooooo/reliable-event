# M4.3：常驻调度与有界并发

> 状态：已完成
> 基线：M4.2 已完成；Java 17、Spring Boot 3.5.16、MySQL 8.0、RocketMQ 5.x
> 目标：Starter 在应用启动后持续恢复过期租约并发布到期事件，以有界线程和队列并发发送；事件只有获得本地执行线程后才能抢占数据库租约。

实施结果与回归数据见 [M4.3 阶段完成记录](../progress/M4_3_COMPLETED.md)。

M4.2 已能装配 `JdbcEventPublicationCycle`，但业务方仍需显式调用 `runOnce()`。当前 `JdbcEventPublicationWorker.publishDueEvents()` 顺序处理候选，发送期间不持有数据库事务。M4.3 在这些已验证的数据库和消息协议之上增加运行时调度，不修改 Outbox 表、状态机、RocketMQ 消息映射或至少一次投递语义。

阶段顺序保持为：

```text
M4.3 常驻调度与有界并发
  → M4.4 停止抢占、等待在途发送与优雅停机
  → M4.5 Micrometer 指标、结构化日志与 M4 总验收
```

## 本阶段冻结的语义

1. 一个应用实例只有一个自动扫描循环。扫描轮次不重叠，但上一轮提交的发送任务可以在下一轮扫描时仍在执行。
2. 每轮先恢复至多 `recovery-batch-size` 个过期租约，再扫描到期事件。恢复失败时本轮不派发发布任务；已经提交的恢复事务不会回滚。
3. 每轮最多向本地执行器提交 `claim-batch-size` 个不同的候选事件，且本地未完成任务总数不得超过 `worker-threads + worker-queue-capacity`。
4. 队列只保存**尚未抢占**的候选快照。任务在线程开始执行后才调用现有条件抢占逻辑，随后在事务外同步发送，最后以版本、Owner 和有效租约更新状态。不得先批量抢占再排队。
5. `worker-threads` 是本实例同时执行候选任务的上限；队列容量只限制等待执行的候选数，不增加同时持有租约的事件数。候选查询、任务排队或提交失败均不增加 `attempt_count`。
6. 同一实例在任务完成前不重复排队同一事件 ID；跨实例仍由数据库条件抢占决定唯一执行权。旧候选版本失效时直接跳过，不在本地强制重试。
7. 现有同步 `JdbcEventPublicationCycle.runOnce()` 及 `PublicationCycleResult` 含义保持不变。自动扫描使用新的异步派发入口，其结果只能表示恢复数和提交数，不能把“已提交任务”当成“已发布消息”。

自动调度不保证消息顺序或硬实时送达。Broker 已接收但 Outbox 状态未更新时仍可能重复发送；下游继续按稳定事件 ID 或 `(eventType, eventKey)` 幂等处理。

## 单轮流程与容量协议

```text
固定延迟触发一个扫描轮次
        ↓
限量恢复过期租约
        ↓
读取本地剩余容量，限量查询到期候选
        ↓
按事件 ID 去除本实例未完成任务，预留本地槽位并提交候选任务
        ↓
执行线程开始任务 → 短事务条件抢占 → 事务外 RocketMQ send
                                           ↓
                         短事务完成 PUBLISHED / RETRY_WAIT / DEAD
                                           ↓
                         finally 释放本地槽位和事件 ID
```

本地槽位从成功预留起覆盖排队和执行两个阶段，在任务结束、被拒绝或关闭时释放。任意时刻满足：

```text
未完成任务数 ≤ worker-threads + worker-queue-capacity
运行中的候选任务数 ≤ worker-threads
本轮成功提交数 ≤ min(claim-batch-size, 派发阶段开始时可用槽位数)
```

`worker-queue-capacity=0` 表示没有等待队列，只向空闲执行线程交付任务。配置值为正时使用有界队列，不使用无界 `LinkedBlockingQueue` 或静默扩容。执行器拒绝任务时撤销本地预留；该候选仍保持原数据库状态，可由后续轮次重新发现。调度线程不得等待队列腾出位置，避免扫描和租约恢复被慢发送长期阻塞。

候选快照在队列中可能变旧。执行时必须重新校验 `status`、`next_attempt_at`、`attempt_count` 和 `version`；现有 `JdbcOutboxRepository.claim(...)` 已包含这些条件。抢占零行属于正常竞争，不调用 Sender，也不计作发送失败。

### 查询窗口与本地去重

每轮至多提交 `min(claim-batch-size, freeSlots)` 个新候选。为了避免查询结果前部被本实例已经排队的 ID 占满，候选查询上限取“本轮可提交数 + 本实例未完成任务数”，再按事件 ID 过滤并按原查询顺序提交。计算上限时检查整数溢出；查询和提交均保持有界。不把数据库查询到的候选数当作已抢占数。

本地去重只减少同一实例的重复排队，不替代数据库版本号协议。任务的事件 ID 必须在队列拒绝、抢占失败、发送成功、发送失败和任务异常时释放；否则该事件会被本实例永久忽略。

### 事务与异常边界

- 恢复继续逐条使用短事务；发布任务的抢占和状态完成各用短事务；RocketMQ `send` 不在数据库事务内。
- Sender 的已分类异常仍由现有 Worker 决定 `RETRY_WAIT` 或 `DEAD`，不由调度器发明第二套重试。
- 执行任务遇到数据库异常、失效租约或未预期异常时，任务边界记录安全摘要并释放本地槽位。调度器不在内存中重试该任务；数据库仍处于 `PUBLISHING` 时由租约恢复接管。
- 扫描或恢复异常应结束本轮并记录错误，后续轮次仍继续运行。不能让一次异常永久取消 Java 定时任务，也不能在紧密循环中立即重试数据库。
- 普通运行日志不得输出 Payload、Header 值或凭据；M4.5 再统一结构化字段和指标。

## 调度时序

使用单个调度线程按固定延迟触发：应用 Context 准备好后尽快开始首轮；一轮完成候选提交后，等待 `poll-interval` 再开始下一轮。这个延迟不等待异步发送任务完成。因此慢发送不会阻塞后续过期租约恢复，但本地槽位满时本轮不再提交新候选。

调度器必须防止同一实例的自动扫描轮次重叠。即使宿主应用提供自己的 `TaskScheduler`，默认实现也不能依赖宿主线程池的偶然串行行为。两个应用实例可以各自扫描同一批候选，唯一执行权仍由 MySQL 条件更新决定。

无需为每条事件创建一个定时任务。未来时间和重试时间仍由 `next_attempt_at` 决定，扫描间隔只影响发现延迟。恢复后写入正数退避的事件通常在后续轮次重新参与抢占，不绕过 `next_attempt_at`。

## 配置与自动装配

在 M4.2 的 `ReliableEventProperties` 中新增：

```yaml
reliable-event:
  scheduling-enabled: true
  poll-interval: 1s
  claim-batch-size: 50
  recovery-batch-size: 50
  worker-threads: 8
  worker-queue-capacity: 200
```

| 属性 | 默认值 | 约束与用途 |
| --- | --- | --- |
| `scheduling-enabled` | `true` | 只控制本项目的自动扫描运行时；`false` 时保留 M4.2 的 Bean 和显式 `runOnce()` |
| `poll-interval` | `1s` | 至少 1 ms，固定延迟；不作为发送超时或租约时长 |
| `worker-threads` | `8` | 正整数，限制并发执行任务数 |
| `worker-queue-capacity` | `200` | 非负整数，限制等待执行的未抢占候选 |

`reliable-event.enabled=false` 仍是总开关：不创建默认发布 Bean、执行器或调度器，也不连接 Broker。用户自定义调度运行时 Bean 时默认实现退让，不重复启动后台循环。属性值在启动时验证，包括 `worker-threads + worker-queue-capacity` 的容量计算不能溢出；错误消息指明具体 `reliable-event.*` 路径。配置元数据和实际绑定测试同步更新，避免 M4.2 的严格未知字段校验拒绝新属性。

自动运行时只在 JDBC 恢复、Worker、事务管理器和 `EventSender` 等依赖可确定时装配。用户提供自定义 `EventSender` 仍可让 JDBC 路径运行，不要求默认 RocketMQ 配置；缺少必需依赖时按 M4.2 条件装配规则退让。Bean 创建本身不应查询 Outbox；启动自动运行后才开始扫描。

现有 `runOnce()` 保持显式同步入口，供测试或停用自动调度的应用使用。开启自动调度时，应用代码不应再自行循环调用它；手动调用不纳入自动执行器的容量统计，虽然数据库条件抢占仍能保护事件状态。

## 生命周期边界

运行时应随 Spring Context 启动，并在 Context 关闭时先停止安排新轮次和接收新候选，关闭本项目创建的调度器与执行器。关闭前尚未抢占的排队任务必须撤销本地预留；已抢占任务即使中断或进程退出，也保持现有租约恢复语义。用户提供的线程池或调度器不由默认运行时擅自关闭。

M4.3 只保证停止后不再产生新的自动抢占，并清理本项目创建的线程资源。等待在途发送完成的时限、Producer 关闭顺序以及超时后的明确策略属于 M4.4，不能把本阶段的基本停止钩子描述成完整优雅停机。

## 与现有代码的接缝

1. 在 `reliable-event-jdbc` 复用 `JdbcOutboxRepository.findDueEventCandidates(...)` 和 Worker 的逐候选处理逻辑，提供最小的“限量扫描”和“执行单个候选”接缝。现有 `publishDueEvents()` 可继续同步遍历，不能让异步路径复制 SQL 或发送状态机。
2. 在自动配置模块新增自动扫描协调器和有界执行器。协调器负责恢复顺序、容量、本地去重、任务提交和轮次异常；Worker 继续负责数据库抢占、发送和状态转换。
3. 为异步轮次使用独立结果模型，例如 `recoveredCount` 与 `submittedCount`。不更改 `PublicationCycleResult.publishedCount` 的既有含义，也不让调度线程等待所有发送结束来凑出发布成功数。
4. 在 Spring Boot 条件装配中接入运行时生命周期与配置属性；保留用户 Bean 覆盖和 `enabled=false` 的既有行为。
5. 不引入新表、租约续期、人工重放或消费者幂等实现。

## 实施顺序

1. 为 JDBC Worker 提取单候选处理入口与限量候选扫描入口，保持同步 `runOnce()` 测试全部通过。
2. 实现本地槽位、事件 ID 去重、有界执行器和异步单轮协调器；先用可控执行器验证排队期间没有数据库抢占。
3. 接入固定延迟调度和 Spring 生命周期，补齐配置、校验、条件装配与关闭时的基本资源清理。
4. 用真实 MySQL 验证容量上限、并发竞争、租约恢复和重复候选；用真实 RocketMQ 验证 Starter 启动后无需显式 `runOnce()` 即可发布。
5. 执行全仓 `mvn clean verify`，在独立的 M4.3 完成记录中填写实际测试数与结果；验收前不修改 README、交接文档或简历中的“仍需显式调用”表述。

## 验收测试

### 单元与 Context 测试

至少覆盖：

1. 固定延迟轮次不重叠，轮次顺序为先恢复、再扫描和派发；恢复失败不派发，而下一轮仍可运行。
2. `worker-threads=1`、队列容量为 `1` 时，阻塞第一个 Sender 并排队第二个候选：第二个候选保持 `PENDING`，`attempt_count=0`，没有租约；第三个候选不进入本地任务集合。释放第一个任务后第二个才抢占。
3. 队列容量为 `0` 时只向空闲线程提交；容量用尽和执行器拒绝都不抢占数据库事件。任务异常释放本地预留，已取得的租约按现有恢复协议处理。
4. 同一事件 ID 在未完成期间只排队一次；旧候选版本在执行时抢占零行，不调用 Sender。
5. Sender 失败仍走现有重试或死信路径；状态完成时租约失效的异常只影响当前任务，后续扫描仍运行。
6. `scheduling-enabled=false` 保留手动 `runOnce()`，不创建后台线程；`enabled=false` 不创建默认 Bean 或连接 Broker；自定义运行时 Bean 不产生第二个调度循环。
7. `poll-interval`、线程数、队列容量非法或容量溢出在启动期失败；新属性从 YAML 正确绑定且配置元数据包含这些键。
8. 没有在途发送时关闭 Context，之后不再自动查询或抢占，项目创建的线程退出；这项测试不宣称已经具备 M4.4 的在途发送等待保证。

### 真实服务测试

沿用现有 MySQL 8.0.36、RocketMQ 5.5.0 和 Testcontainers 夹具：

- 最小 Spring Boot 应用通过 Starter 在事务内登记事件，不调用 `runOnce()`；在有界期限内从 Broker 消费并核对 Topic、Tag、Key、Body、稳定事件属性及 Outbox `PUBLISHED`。
- 两个独立运行时扫描同一候选时，真实 MySQL 中只有一个 Worker 成功抢占并发送；版本和租约 Owner 保护仍成立。
- 人为阻塞发送并制造超过本地容量的积压，确认同时 `PUBLISHING` 的任务不超过执行线程数，排队候选尚未持有租约；解除阻塞后积压继续推进。
- 过期 `PUBLISHING` 事件由自动轮次恢复，并在退避到期后重新发布；失败重试和 `DEAD` 终态不因并行处理而改变。

测试使用同步器、明确的数据库状态和有截止时间的等待条件；不通过固定 `sleep` 猜测线程或 Broker 的进度。全部既有 M0 至 M4.2 测试仍须通过，最终数量记录在完成文档中。

## 完成边界

M4.3 完成后可以说“Starter 启动后自动持续扫描，并通过有界线程与队列并发发布”。仍不能承诺 Exactly Once、消息顺序、硬实时调度、完整优雅停机、租约续期、人工死信重放或 Micrometer 指标。M4.4 负责在途发送等待和关闭顺序，M4.5 负责指标、结构化日志与 M4 总验收。
