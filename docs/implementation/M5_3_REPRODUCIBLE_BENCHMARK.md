# M5.3：可复现基准测试交接

> 状态：已完成。本文件保留测试与交付协议；运行入口见[基准模块说明](../../reliable-event-benchmark/README.md)，实测结果与原始证据见[完成记录](../progress/M5_3_COMPLETED.md)。
>
> 基线：M5.1 已完成；2026-09-26 范围更新后，M5.2 私有业务验收已取消。
>
> 目标：在真实 MySQL 8.0 与 RocketMQ 5.x 上，用仓库内可重复执行的脚本测量事件登记与后台发布的吞吐、延迟和数据库成本，并保留原始结果、配置及执行计划。结果用于判断当前实现的容量边界，不预设性能目标。

## 接手时的项目状态

- 父工程使用 Java 17 编译目标、Spring Boot 3.5.16；MySQL Connector/J 为 8.0.33，现有集成测试使用 MySQL 8.0.36，RocketMQ 测试环境使用 5.5.0，Java 客户端版本为 5.2.1。运行 JDK、Docker 和宿主机版本应以本次实测环境重新记录。
- Starter 默认每秒扫描一次，配置项包括 `poll-interval`、`claim-batch-size`、`recovery-batch-size`、`worker-threads`、`worker-queue-capacity`、`lease-duration`、`max-attempts`。执行线程开始后才条件抢占；本地未完成任务受线程数与队列容量限制。参考 [M4.3 实施协议](M4_3_SCHEDULING_AND_BOUNDED_CONCURRENCY.md)。
- Outbox 表已有 `(status, next_attempt_at, id)` 发布扫描索引和 `(status, lease_until, id)` 租约恢复索引。候选查询按 `next_attempt_at, id` 排序；抢占、成功更新和恢复均是条件更新。参见 [正式建表 SQL](../../reliable-event-jdbc/src/main/resources/schema/reliable-event-outbox.sql)。
- `reliable_event.publish.duration` 仅测量单次 `EventSender.send`；`reliable_event.publish.lag` 从首次计划可用时间到成功回执，包含排队与失败等待，但不代表 Outbox 已更新为 `PUBLISHED`。`backlog` 包含未来待发事件，多个实例的数据库 Gauge 不能求和。参见 [M4.5 指标协议](M4_5_OBSERVABILITY_AND_M4_ACCEPTANCE.md)。
- 仓库已有可运行的[原创订单示例](../../reliable-event-example/README.md)和独立[基准模块](../../reliable-event-benchmark/README.md)。M5.1 记录的 134 个测试通过是历史回归结果，不是 M5.3 的性能证据。

## 本阶段范围与交付物

在本仓库新增独立的 `benchmark/` 目录或 Maven 模块，提供：

1. 固定服务版本的启动配置与准备脚本：建立独立测试数据库、正式 Outbox 表、RocketMQ Topic，检查 Broker/Proxy 路由真正可用；禁止依赖私有优惠券项目或生产环境。
2. 数据构造与负载驱动：通过公开 `ReliableEventPublisher` 在真实 Spring 事务内登记唯一事件；使用默认 Starter 和真实 `RocketMqEventSender` 完成发布。区分预置历史行与本轮待发布行，不让建表、造历史数据或镜像拉取时间混入测量窗口。
3. 原始结果采集：每轮保存配置、环境、时间戳、每秒状态与资源样本、事件级或直方图延迟、最终数据库状态、Broker 接收证据、SQL `EXPLAIN ANALYZE` 原文。原始文件使用可机器读取格式，例如 CSV/JSON；报告可由原始文件重新生成。
4. 一份仓库内的结果报告，列出执行命令、有效样本、重复轮次、聚合方法、吞吐、P50/P95/P99、数据库 CPU/连接/锁等待、失败与重复情况，以及未达到完成条件的轮次。没有数据的指标明确写“未测得”，不填估计值。
5. 独立的 M5.3 完成记录。只有脚本、原始证据和回归测试都齐备后，才能将阶段状态改成已完成。

本阶段可增加基准专用探针与脚本，但不能为追求漂亮数字绕开事务登记、替换成 Fake Sender、直接把行更新为 `PUBLISHED`，或悄悄改变正式发布状态机。需要优化生产代码时，先保留修改前基线，再单独记录改动与同条件复测。

## 固定测量口径

| 指标 | 计算与来源 | 不能混用的口径 |
| --- | --- | --- |
| 登记吞吐 | 测量窗口内成功提交的唯一 Outbox 事件数 ÷ 窗口秒数 | API 调用数、重复键返回数、构造对象数 |
| 发布吞吐 | 稳态窗口内新增 `PUBLISHED` 的唯一事件数 ÷ 窗口秒数；另报从启动发布到本轮全部终态的整体完成时间 | Sender 成功回执数、线程池提交数、Broker 收到的消息条数 |
| 首次可用到回执延迟 | 使用现有 `publish.lag` 的口径：`first_available_at →` 每次成功回执；报告有效样本数，并注明它不包含随后状态更新，且同一事件可能产生多个样本 | `publish.duration`、未来事件的登记时间 |
| 首次可用到状态时间差 | 本轮 `PUBLISHED` 事件的 `published_at - first_available_at`；列出 P50/P95/P99 和样本数。`published_at` 由应用在状态更新前取时钟值，不能当作数据库提交的精确时刻 | 消费者完成时间、严格的事务提交到发布延迟 |
| 发送耗时 | `publish.duration`，按成功、可重试、不可重试和结果未知分别统计 | 端到端发布延迟 |
| 失败率 | 失败的 Sender 尝试数 ÷ 全部 Sender 尝试数，同时列出 `RETRY_WAIT`、`DEAD` 与最终未完成事件数 | 把结果未知直接断言为 Broker 未接收 |
| 重复率 | 从本轮 Broker 消息按稳定 `reliable_event_id` 分组：额外消息数 ÷ 收到的消息总数；同时列出重复事件身份数。若接收探针无法证明覆盖全部消息，报告为“不完整样本” | 按 Broker Message ID 去重或把重复率当成并发抢占失败率 |

延迟分位数只对完整的本轮有效样本计算，保留每轮原始分布，不将几轮的 P99 直接平均成总 P99。应从合并的事件级样本重新计算总体分位数，或只逐轮展示。生产数据库字段为 `DATETIME(3)`，毫秒精度与应用时钟偏差会影响短延迟；报告要记录时钟同步检查、负值样本数和处理方式。`first_available_at` 早于事务提交时，以上延迟包含登记事务尚未提交的时间，不能称作严格的“提交到发布”延迟。若另测事务提交返回到发布完成，使用基准专用探针，单独命名并说明探针开销与跨进程时间基准。

稳态吞吐窗口从预热后开始，排除启动连接、Topic 路由建立和最后排空阶段；窗口开始与结束规则须写入脚本，不能查看结果后临时挑选最快片段。完整批次的总量、开始时间、结束时间及状态守恒检查也要保留，避免只报告峰值。每个配置至少独立运行三轮；固定 Payload 字节数、Header 数量和事件类型，并保留消息大小的实际统计。

## 最小实验矩阵

先跑基线，再一次只改一个维度。默认值来自当前 `ReliableEventProperties`；最终报告写实际生效值，不只贴配置文件。

| 组别 | 工作负载和变量 | 要回答的问题 |
| --- | --- | --- |
| A：单实例基线 | 1 个 Starter 实例、默认配置；一批 1 万条立即可用事件，固定 Payload | 正常路径的吞吐、延迟分布、资源占用和状态守恒 |
| B：表规模 | 同样的 1 万条本轮事件；分别预置总表规模约 1 万、10 万、100 万行的历史 `PUBLISHED` 数据，并采集候选查询、租约恢复查询与状态聚合查询的 `EXPLAIN ANALYZE` | 表增长后索引扫描、指标采样和数据库成本如何变化 |
| C：调度容量 | 保持工作负载与表规模不变，分别调整轮询间隔、批次、线程数、队列容量；每次只改一项 | 容量瓶颈位于扫描、抢占、本地队列还是 Broker 发送 |
| D：多实例 | 2 个相同实例共用同一 MySQL 与 Topic，总工作量与单实例组相同 | 总吞吐、资源成本、竞争开销以及同一事件是否被并发抢占 |
| E：可控故障 | 单独运行 Broker/Proxy 暂时不可用和成功后丢弃回执两个场景，固定故障时长与注入位置 | 退避后的排空时间、尝试数、结果未知重复消息和死信情况 |

表规模组的历史行需与本轮事件身份可区分；测试不得把大量未到期 `PENDING` 行误认为“历史已发布行”。若需要测量活跃积压规模，作为额外实验单列。1 万、10 万、100 万是[项目方向文档](../PROJECT_DIRECTION.md#18-基准测试)要求的索引规模，不代表每组都必须向 Broker 再发送 100 万条消息。为减少噪声，各组开始前检查数据库与 Broker 就绪，固定资源限制、Topic、连接数、消息体、预热和采样区间；容器与宿主机资源争用要记录。

## 资源与正确性证据

- 每轮记录 CPU 型号、核心数、内存、磁盘类型、操作系统、Docker/容器资源限制、JDK/Maven、MySQL 服务端与驱动、RocketMQ Broker/Proxy 与客户端版本、应用实例数、Git commit、是否有工作区改动。容器镜像应固定版本，正式报告保存镜像摘要。
- 以有固定采样周期的原始序列记录 MySQL CPU、活动/总连接、锁等待、InnoDB 行锁或事务等待、磁盘读写、Broker/Proxy 与应用 CPU/内存。指标来源和采样命令写入脚本；拿不到的指标明确标缺失，不用主机总体 CPU 冒充 MySQL CPU。
- 在测量前后保留三类 SQL 原文和执行计划：到期候选扫描、过期租约扫描、`PENDING/RETRY_WAIT/DEAD` 状态聚合。记录表行数、索引选择、实际扫描行数与耗时。`EXPLAIN ANALYZE` 本身消耗资源，应在独立观察窗口运行，不计入吞吐测量。
- 核对本轮唯一事件数等于 `PENDING + PUBLISHING + RETRY_WAIT + PUBLISHED + DEAD` 的本轮行数；健康组最终应全部 `PUBLISHED`、无遗留 `PUBLISHING/RETRY_WAIT/DEAD`。若不成立，报告实际状态并判该轮无效，不删除异常行制造通过结果。
- Broker 接收探针需保存稳定事件 ID、业务 Key、Broker Message ID 与接收时间，避免只凭发送计数宣称无重复。消费者 ACK、示例业务处理完成与生产端 `PUBLISHED` 是不同事实；M5.3 的主要对象是发布端，不把它描述为私有优惠券业务验收。
- 故障组记录故障开始、恢复、首次失败、再次发送、最终状态的时间线；结果未知允许重复投递。并发抢占安全与故障后至少一次投递是不同断言。

## 实施顺序

1. 建立隔离环境与基准负载驱动，先以少量事件核对事务内登记、真实 Broker 接收、状态守恒、时钟和采样字段；确认脚本重复执行不会混入前轮事件。
2. 固定环境配置、事件载荷和窗口规则，采集 A 组的三轮原始数据。将环境初始化、预热、测量、排空、采样与报告生成拆开，使每段可重跑。
3. 构造 B 组历史表规模并采集独立执行计划；再按单变量方式执行 C、D 组。每组保存原始文件，即使性能下降或轮次失败也保留。
4. 执行 E 组故障与重复验证。故障结束后按截止时间等待最终状态，不以固定睡眠时长当作恢复证明。
5. 从原始数据生成报告，核对每个表格数字可追溯到文件与脚本。运行全仓 `mvn verify`，记录本次真实测试数及结果；另写 M5.3 完成记录，再更新 README/交接中的阶段状态。

## 验收标准与交接边界

- 从仓库文档给出的命令可以在隔离环境完成初始化、负载、采样、报告生成与资源清理；不需要手工改 SQL、私有项目或生产数据库。脚本有超时、失败退出码和可定位的日志。
- A 至 D 组至少各有三轮有效结果，E 组有故障时间线和真实 Broker 身份证据；1 万、10 万、100 万表规模下的三类查询均有原始执行计划。
- 报告包含登记吞吐、发布吞吐、P50/P95/P99、MySQL CPU/连接/锁等待、失败率与重复率，或者明确说明某项未能可靠测得及原因；不能只给聚合图而丢失原始样本。
- 健康组状态守恒通过；故障组清楚区分恢复、死信、结果未知和预期重复。全仓回归通过且不修改至少一次语义。
- 对外只引用附有环境、配置、样本量与复现命令的结果。M5.2 已取消，不属于 `0.1.0` 发布条件；M5.3 完成也不自动满足其余发布条件，后续检查属于 M5.4。
