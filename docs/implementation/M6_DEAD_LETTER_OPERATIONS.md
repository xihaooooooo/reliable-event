# M6：死信查询与受控重放总计划

> 状态：进行中；M6.1 已完成。本文只确定 M6 的目标、范围和拆分方向；接口、表结构、状态转换及测试细节由后续小计划确定。
>
> 前提：现有 `DEAD` 事件不会自动再次发布，也没有人工重放接口。M6 是后续开发里程碑，不改变 `0.1.0` 的范围或 M5.4 暂缓正式发布的结论。

## 目标

让运维人员在事件进入 `DEAD` 后，能够定位失败、修复原因、显式申请单条重放，并追踪操作与发布结果。重放复用现有的扫描、条件抢占、发送和重试链路，不建立第二套发送流程。

## 范围与边界

- 提供死信列表和单条详情查询，展示事件身份、状态、尝试次数、时间及受控的失败摘要；默认不暴露 Payload 和 Headers。
- 提供单条 `DEAD` 事件的受控重放能力。只有当前状态和版本符合预期时才能重新入队；并发或重复操作不得产生多次有效重放。
- 持久记录重放操作者、原因、时间和操作结果，并提供重放后的状态追踪。调用方负责限制操作权限，库提供可审计的操作接缝。
- 保留原事件身份和至少一次投递语义。对于发送结果未知的事件，重放可能产生重复消息，操作前须核对 Broker 与消费者侧事实。
- 本阶段不做自动重放、批量重放、管理后台、AI 分析，也不处理 RocketMQ 消费端死信队列。已有 `reliable_event.dead` 指标可用于告警，M6 不内置告警平台。

## 小计划划分

1. **[M6.1：死信查询与排障信息](M6_1_DEAD_EVENT_QUERY.md)。** 提供只读列表和详情，确定分页及敏感字段边界。
2. **[M6.2：单条重放与原子审计](M6_2_CONTROLLED_REPLAY.md)。** 实现带版本保护的重新入队；成功重放与审计记录同事务提交。
3. **[M6.3：Starter 接入与人工操作流程](M6_3_STARTER_OPERATIONS.md)。** 让接入应用能使用查询和重放能力，给出授权、排查和结果追踪示例。
4. **[M6.4：端到端验收与交接](M6_4_ACCEPTANCE.md)。** 在真实 MySQL 与 RocketMQ 上验证重放、竞态和重复投递边界，完成运维文档。

## 完成标准

从一条真实 `DEAD` 事件出发，操作者可以查询原因、修复外部问题、执行一次受控重放，并通过审计记录和最终状态复核全过程。非 `DEAD` 事件和过期版本请求不能被重放；M6 新路径通过自动化测试，文档明确重放权限、重复消息风险和人工处置步骤。
