# M7：已发布事件保留与清理计划

> 状态：M7.1 至 M7.3 已完成；验证结果与上线边界见 [M7 完成记录](../progress/M7_COMPLETED.md)。本计划只涉及生产端 Outbox，不增加消费端功能。

## 目标与依据

将已发布事件的完整记录保留一段可配置的时间，到期后分批从 `reliable_event_outbox` 清理，同时永久保留 `(event_type, event_key) → event_id` 的登记身份。清理前后，同一业务事件重复调用 `publish` 都必须返回原 `EventId`，不能生成第二条待发布记录。

当前 Outbox 同时保存 Payload、Headers、发送状态和唯一登记键；`JdbcOutboxRepository.insert` 依赖 `uk_event_identity` 返回既有 ID。直接删除 `PUBLISHED` 行会让相同业务键重新登记。现有 M5.3 基准在约 100 万历史行下未观察到显著发布速率下降，所以本功能的主要收益是控制主表、索引、备份及排障数据的长期规模，不把吞吐提升列为验收承诺。

## 冻结的语义

- 身份保留期在本阶段为永久。完整 Outbox 行的保留期与身份保留期是两回事；本阶段不提供身份到期删除。若业务要表达一件新的事件，必须使用新的 `eventKey`。
- 重复登记始终返回最初的 `EventId`，不覆盖旧事件的 Payload、Headers 或可用时间。即使原 Outbox 行已清理，也不能重新入队。
- 仅 `PUBLISHED` 且 `published_at` 早于截止时间的行可清理。保留期从 `published_at` 计算，使用数据库 UTC 时间。`PENDING`、`PUBLISHING`、`RETRY_WAIT` 和 `DEAD` 均不清理。
- `PUBLISHED` 只表示生产端成功记录发送回执，不证明消费端完成。本计划不提供消费端 Inbox、消费结果核验或消费端去重记录清理。
- 本阶段不建设完整 Payload 的在线归档表。需要长期保存完整消息的部署方应先明确备份与合规保留要求，再开启清理；清理后公开的死信查询和重放接口不作用于已发布历史行。

## 数据与登记协议

1. 新增 `reliable_event_identity` 表，保存 `id BIGINT`、`event_type`、`event_key`、登记时间。`id` 是原 `EventId`，`(event_type, event_key)` 保持唯一；不复制 Payload、Headers 或发送状态。新增迁移 SQL 和表结构校验，库仍不自动建表。
2. 迁移时把**全部**现存 Outbox 行的 ID 与业务身份写入身份表，包括尚未发布和死信行；核对每一条 Outbox 行都能找到 ID、类型、业务键完全一致的身份，且没有一组业务键对应两个 ID。将身份表自增起点置于现有最大事件 ID 之后。
3. 修改 `publish` 的 JDBC 登记路径：在调用方既有业务事务中先尝试插入身份；新身份取得 ID 后，以相同 ID 插入 Outbox 行。身份已存在时，以锁定读取取得原 ID 并直接返回，不插入 Outbox。并发相同业务键必须由数据库唯一约束裁决；事务回滚时身份和 Outbox 一起回滚。仅把身份唯一键冲突当作重复登记，其他数据库错误继续失败。
4. Outbox 原有唯一键继续保留，作为额外约束。发送、租约、重试和死信状态机继续使用原 Outbox ID；不得在身份已存在但 Outbox 行缺失时重建发送记录。

## 上线与回退顺序

1. 在清理关闭的状态下创建身份表。切换写入协议前暂停事件登记入口，等待在途业务事务结束；回填全部旧数据并完成双表一致性核对。保持登记暂停，直到所有应用实例都部署带新登记协议的版本，再恢复登记。不能让旧版只写 Outbox 的实例与清理任务并行。
2. 先观察新协议的重复登记、回滚和并发行为；逐条核对新增 Outbox 行都有对应身份。只有全量和新增数据的核对均通过，才单独打开清理开关。
3. 清理开始后，旧版发布器不能直接回滚上线：它看不到已清理事件的身份，可能再次登记。回退清理任务只需关闭开关；发布器回退必须仍使用身份表协议。备份和恢复需要使身份表、Outbox 表及重放审计处于相容的数据时间点。身份表不可用时应明确失败，不能降级为旧的 Outbox-only 登记。

## 分批清理

- Starter 增加默认关闭的清理开关；开启时要求显式配置正数保留期，并提供批量上限与执行间隔。参数必须校验，避免零保留期或无界批量。JDBC 模块提供可单次执行、返回扫描/删除数量的清理入口，便于测试和受控运行。
- 增加适合 `status + published_at + id` 的候选索引。每次仅取有限数量的到期 ID，按 ID 稳定推进；删除语句再次校验 `status=PUBLISHED` 和 `published_at<截止时间`，并确认对应身份仍存在且匹配。每批短事务提交，失败后允许重试；不同实例同时执行只能造成有限的重复扫描，不能误删或重复发送。
- 不在发布调度的发送事务中做清理。控制每轮工作量和执行频率，记录清理数量、耗时、失败以及最老待清理记录的年龄；日志不输出业务键、Payload 或 Headers。删除后的物理空间回收与备份策略由数据库运维另行安排。
- 现有运维 SQL 如通过内连接 Outbox 查询重放审计，需改为能显示“历史 Outbox 已清理”的结果；不能把缺少 Outbox 行误判为审计丢失。
