# M2.2 阶段完成记录

## 这一阶段做了什么

- 从 Worker 中提取包内可见的候选处理入口，使扫描和处理候选成为两个明确步骤；
- 保持原有 `publishDueEvents()` 行为，由它扫描到期事件后委托候选处理入口；
- 创建两个独立 Worker，让它们在不同线程中处理同一个候选版本；
- 使用两个 `CountDownLatch` 确认双方就绪并统一开放并发起点；
- 使用线程安全的 Fake Sender 统计发送次数和发送内容；
- 为所有并发等待设置超时，并在 `finally` 中关闭测试线程池。

## 现在证明了什么

在真实 MySQL 5.7 中，两个 Worker 即使持有相同事件 ID 和相同候选版本，也只有一个条件更新能够成功。失败的 Worker 会跳过发送，不会增加尝试次数，也不会覆盖获胜 Worker 的结果。

这证明了 M2.1 的版本号条件抢占能够在双 Worker 同时竞争时提供唯一执行权，而不只是按顺序调用时表现正确。

## 验证结果

使用 Java 17 和 MySQL 5.7.44 Testcontainers 执行测试，9 个集成测试全部通过。新增并发测试验证：

- 两个 Worker 返回的发布数量分别为 `1` 和 `0`；
- Fake Sender 总调用次数为 `1`；
- 最终事件状态为 `PUBLISHED`；
- `attempt_count = 1`；
- 最终 `version = 2`；
- `published_at` 已写入。

测试不依赖具体哪个 Worker 获胜，也没有使用 `Thread.sleep()` 控制时序。

## 当前边界

- 单个 Worker 内部仍然顺序处理候选事件，没有并行线程池；
- 尚未提供后台定时调度；
- 发送失败后事件仍会暂时停留在 `PUBLISHING`；
- 尚未实现 `RETRY_WAIT`、指数退避、最大尝试次数和 `DEAD`；
- 尚未实现租约所有权和宕机恢复。

双 Worker 测试证明的是同一时刻的抢占排他性，不代表已经解决抢占成功后的进程退出问题。

## 下一步

进入 M2.3，实现失败后的 `RETRY_WAIT` 状态、带随机抖动的指数退避、下一次可尝试时间，以及未到重试时间不能再次抢占的测试。
