# M2.3 阶段完成记录

## 这一阶段做了什么

- 增加 `RETRY_WAIT(3)`，并允许到期的 `PENDING` 和 `RETRY_WAIT` 事件参与扫描和条件抢占；
- 在抢占结果中携带数据库递增后的 `attempt_count`；
- 实现带 0%～20% 随机抖动的指数退避，并对增长过程进行饱和计算；
- 为退避组件提供可注入随机源，使时间算法能够确定性测试；
- 捕获 Sender 抛出的 `RuntimeException`，通过短事务将事件更新为 `RETRY_WAIT`；
- 写入下一次尝试时间、截断后的错误摘要，并使用抢占版本保护失败状态更新；
- 单个事件发送失败后继续处理同批次其他候选；
- 重试成功后保留最近一次 `last_error`，由最终状态表达当前结果。

## 现在能够完成什么

```text
PENDING → PUBLISHING → RETRY_WAIT
                         ↓ 到期后重新抢占
                     PUBLISHING → PUBLISHED
```

第一次发送失败后，事件不会继续停留在 `PUBLISHING`，也不会立即高频重试。Worker 会根据本次持久化尝试次数计算下一次时间；到期前扫描不到该事件，到期后可以再次抢占并发送。

## 验证结果

使用 Java 17 和 MySQL 5.7.44 Testcontainers 执行 `mvn clean verify`，共 19 个测试全部通过：

- 7 个单元测试覆盖指数增长、最大基础延迟、确定性抖动、非法配置、错误摘要和 Unicode 安全截断；
- 12 个集成测试覆盖原有事务、幂等、条件抢占和双 Worker 竞争，以及新增的失败等待、提前扫描不重试、到期重试成功、旧版本失败更新拒绝和同批次继续处理。

重试成功场景验证了两次抢占和两次完成状态：最终 `attempt_count = 2`、`version = 4`。

## 当前边界

- 尚未根据 `max_attempts` 终止重试；
- 尚未实现 `DEAD` 和不可重试错误分类；
- Sender 抛出的所有 `RuntimeException` 暂时都按可重试错误处理；
- 进程在抢占后直接退出时，事件仍可能停留在 `PUBLISHING`；
- 尚未实现租约、宕机恢复、后台调度和并行线程池。
