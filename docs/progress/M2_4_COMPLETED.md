# M2.4 阶段完成记录

## 这一阶段做了什么

- 增加 `DEAD(4)`，完成 M2 状态机闭环；
- 明确 `max_attempts` 表示最大总发送次数，并将逐事件上限带入抢占结果；
- 在候选扫描和条件抢占中同时校验 `attempt_count < max_attempts`；
- 增加显式可重试、不可重试发送异常语义和内部分类组件；
- 未知普通 `RuntimeException` 默认按可重试处理，不根据异常消息文本分类；
- 可重试错误在次数耗尽后进入 `DEAD`，不可重试错误第一次失败即可进入 `DEAD`；
- 死信更新保存错误摘要、校验抢占版本并递增版本号；
- `DEAD` 事件不再参与自动扫描，一个事件死信后继续处理同批次其他候选。

## 现在能够完成什么

```text
PENDING → PUBLISHING → PUBLISHED
              │
              ├────→ RETRY_WAIT → PUBLISHING
              │
              └────→ DEAD
```

每条事件使用自身持久化的 `max_attempts`。最后一次允许发送如果成功，事件仍进入 `PUBLISHED`；只有发送失败且次数已经耗尽，或者错误被明确标记为不可重试时，才进入 `DEAD`。

## 验证结果

使用 Java 17 和 MySQL 5.7.44 Testcontainers 执行 `mvn clean verify`，共 27 个测试全部通过：

- 10 个单元测试覆盖指数退避、错误摘要、Unicode 截断和发送错误分类；
- 17 个集成测试覆盖事务原子性、幂等登记、条件抢占、双 Worker 竞争、延迟重试、重试耗尽、不可重试错误、死信终态和版本保护。

重点验证：

- `max_attempts = 2` 时，第二次可重试失败进入 `DEAD`，最终 `attempt_count = 2`、`version = 4`；
- 第二次发送成功时仍进入 `PUBLISHED`；
- 不可重试错误第一次失败直接进入 `DEAD`，且不消费退避随机数；
- `DEAD` 事件之后不会再次调用 Sender；
- 已达到上限的异常 `RETRY_WAIT` 记录不能被扫描或抢占；
- 旧抢占版本不能覆盖当前状态写入死信。

## M2 已经证明的能力

- MySQL 5.7 版本号条件抢占；
- 双 Worker 并发竞争时的唯一执行权；
- 发送失败后的指数退避和随机抖动；
- 未到重试时间不发送；
- 最大总发送次数；
- 可重试和不可重试错误分类；
- `PUBLISHED` 与 `DEAD` 终态。
