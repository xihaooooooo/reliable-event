# M3.2 阶段完成记录

## 这一阶段做了什么

- 新增不可变 `ExpiredLeaseCandidate`，保存事件 ID、版本、租约 Owner、截止时间、尝试次数和最大次数；
- 使用 `status + lease_until` 索引限量查询已经过期的 `PUBLISHING` 记录；
- 查询和恢复更新统一使用 MySQL `UTC_TIMESTAMP(3)` 判断租约是否过期；
- 恢复更新同时校验事件 ID、状态、版本、Owner 和截止时间快照；
- 有剩余尝试次数的事件恢复为 `RETRY_WAIT`，并按当前尝试次数计算退避；
- 已耗尽尝试次数的事件恢复为 `DEAD`，且不计算退避；
- 恢复成功后清空租约字段、递增版本并保存独立的租约过期原因；
- 恢复动作不增加 `attempt_count`，也不调用 Sender；
- 新增独立 `JdbcExpiredLeaseRecovery`，每个候选使用短事务恢复，失效候选按正常竞争返回失败；
- Owner 或截止时间缺失的异常 `PUBLISHING` 记录不会被自动修复。

## 现在证明了什么

已经失去有效 Owner 的 `PUBLISHING` 事件可以通过显式恢复入口重新进入状态机，同时不会覆盖以下变化：

- 数据库版本已经前进；
- 租约 Owner 已改变；
- 租约被延长到未来；
- 租约截止时间已被替换为另一份快照；
- 同一过期候选已经被其他恢复操作处理。

恢复后的事件不会立即高频重试。`next_attempt_at` 使用数据库恢复时间加指数退避生成，到期前不能重新抢占，到期后可以由新 Worker 获取新租约。

## 验证结果

使用 MySQL 8.0.36 Testcontainers 执行 `mvn clean verify`，共 46 个测试全部通过：

- 20 个单元测试覆盖原有退避、错误摘要、失败分类、租约令牌，以及新增的过期候选不变量和恢复组件配置；
- 26 个集成测试覆盖原有事务、幂等、抢占、重试、死信和租约所有权，以及新增的过期租约恢复场景。

新增集成测试重点验证：

- 活跃租约不会被查询或恢复；
- 过期租约在仍有次数时进入 `RETRY_WAIT`；
- 恢复退避使用数据库时间，并且到期前不能重新抢占；
- 恢复后的新抢占使用新的 Owner、版本和尝试次数；
- 次数耗尽的过期租约直接进入 `DEAD`，且不消费随机源；
- 同一过期候选只能成功恢复一次；
- 版本、Owner 或截止时间变化后旧候选更新失败；
- 单轮恢复遵守批次上限和最早过期优先顺序；
- Owner 或截止时间不完整的异常记录保持不变。

## 当前边界

- 恢复组件需要显式调用，尚未纳入普通发布循环的单轮编排；
- 尚未执行两个恢复 Worker 使用同一候选的真实并发测试；
- 尚未验证旧发送 Worker、恢复 Worker 和新抢占 Worker 的交错竞态；
- 尚未执行独立 JVM 抢占后退出和发送后退出故障注入；
- 没有租约续期、后台调度、并行线程池和恢复指标；
- 无 Owner 或截止时间的异常 `PUBLISHING` 记录只会被跳过，不会自动猜测或修复。

因此当前可以表述为已实现“过期租约条件恢复机制”，不能提前表述为完整多实例宕机恢复已经完成。

## 下一步

进入 M3.3，冻结单轮恢复与发布顺序，并通过真实 MySQL 并发测试验证：同一过期租约只有一个恢复者成功，恢复或重新抢占后旧 Worker 不能覆盖新的状态。
