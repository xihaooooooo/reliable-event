# M3.3 阶段完成记录

## 这一阶段做了什么

- 新增同步、包内可见的 `JdbcEventPublicationCycle`，将单轮执行顺序固定为先恢复过期租约、再发布普通到期事件；
- 新增不可变 `PublicationCycleResult`，分别返回本轮恢复数量和成功发布数量；
- 恢复与发布继续各自只处理一个有界批次，没有增加跨阶段事务、循环、休眠、调度器或线程池；
- 为 `JdbcExpiredLeaseRecovery` 增加显式候选入口，并在开始处理前复制和校验候选列表；
- 生产恢复入口继续自行限量查询，然后复用同一候选处理逻辑；
- 两个恢复者可以在测试中使用完全相同的过期候选快照，条件冲突仍按正常竞争返回零行；
- 新增可阻塞 Fake Sender，使用门闩精确控制旧 Worker、恢复者和新 Worker 的执行顺序；
- 并发测试全部使用超时和显式同步，不使用 `Thread.sleep(...)` 猜测线程时序。

## 现在证明了什么

单轮执行已经具有明确而有界的内部入口：先处理失去有效所有者的 `PUBLISHING` 记录，再扫描普通 `PENDING` 和 `RETRY_WAIT` 事件。两个阶段不共享总事务，Sender 继续位于数据库事务外。

两个独立恢复者使用同一份候选快照并发更新时，只有一个恢复者能够成功：

- 可重试事件只进入一次 `RETRY_WAIT`；
- 次数耗尽事件只进入一次 `DEAD`；
- 版本只增加一次；
- 恢复不增加 `attempt_count`；
- 失败恢复者不能覆盖获胜者写入的状态。

旧 Worker 阻塞在 Sender 期间租约过期后，恢复者可以让事件重新进入状态机。旧 Sender 随后即使返回成功，也不能使用旧版本和旧 Owner 写入 `PUBLISHED`。事件被新 Worker 再次抢占后，旧 Worker 同样不能覆盖新租约；新 Worker仍能正常完成发布。

## 验证结果

使用 MySQL 8.0.36 Testcontainers 执行 `mvn clean verify`，共 58 个测试全部通过：

- 27 个单元测试覆盖原有退避、错误摘要、失败分类、租约令牌、过期候选，以及新增的单轮结果、编排顺序、异常传播和显式候选入口；
- 31 个集成测试覆盖事务、幂等、抢占、重试、死信、租约所有权、过期恢复，以及新增的单轮编排和并发接管场景。

本阶段新增的 5 个 MySQL 集成测试重点验证：

- 单轮能够恢复过期租约，并继续发布普通到期事件；
- 两个恢复者竞争同一可重试候选时只有一个成功；
- 两个恢复者竞争同一耗尽候选时只有一个写入死信，且不计算退避；
- 旧 Sender 返回成功时不能覆盖已经恢复的状态；
- 恢复后新 Worker 可以获得新租约，旧 Worker 不能覆盖它，最终由新 Worker 完成发布。

## 当前边界

- 单轮入口仍需显式调用，没有后台定时调度；
- Worker 内仍然顺序发送，没有有界并行线程池；
- 并发接管测试在同一测试进程内通过同步器构造，还没有主动终止独立 JVM；
- 尚未验证“抢占提交后、Sender 调用前退出”的独立进程故障场景；
- 尚未验证“Sender 成功后、状态更新前退出”产生的重复发送窗口；
- 没有租约续期、RocketMQ 生产适配、Spring Boot 自动配置、指标或死信人工重放。

因此当前可以表述为已经完成“多恢复者并发接管验证和新旧 Worker 所有权栅栏测试”，但还不能表述为完成了独立进程故障注入或消除了重复消息。
