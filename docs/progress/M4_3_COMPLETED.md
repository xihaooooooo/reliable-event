# M4.3 阶段完成记录

## 已实现

- Spring Boot Starter 默认启动单个固定延迟扫描循环；每轮先限量恢复过期租约，再按本地剩余容量派发到期候选。`scheduling-enabled=false` 保留 M4.2 的显式 `runOnce()` 模式。
- 新增固定大小发送线程池、有界候选队列和本地事件 ID 去重。未完成任务数不超过 `worker-threads + worker-queue-capacity`，每轮提交数不超过 `claim-batch-size`；队列容量可设为 `0`。
- 队列只保存候选快照，执行线程开始任务后才在短事务中条件抢占。抢占后仍在事务外调用 Sender，并以原有版本、Owner 和有效租约协议完成状态更新；排队、拒绝和旧候选竞争失败均不增加尝试次数。
- 调度异常不会永久取消后续轮次，任务结束、异常、拒绝或关闭时释放本地槽位。关闭与短事务抢占之间增加同步栅栏，停止后不再开始新的自动抢占。
- 新增 `poll-interval`、`worker-threads`、`worker-queue-capacity` 和 `scheduling-enabled` 属性及启动期校验；配置元数据包含新属性。原有同步单轮入口和 `publishedCount` 含义保持不变，异步轮次单独记录恢复数与提交数。

## 验证

- 单元和 Context 测试验证排队期间尚未抢占、本地容量上限、扫描异常后的下一轮继续执行、禁用调度、自定义 Sender 与运行时覆盖，以及非法配置启动失败。
- 真实 MySQL 集成测试验证一个执行线程加一个队列槽位时，排队候选保持 `PENDING`、`attempt_count=0`，且没有租约；解除阻塞后积压继续完成。
- Starter 端到端测试验证无需显式 `runOnce()` 即可从真实 RocketMQ 5.5.0 消费消息；过期租约可由自动轮次恢复并再次发布；两个自动调度的应用 Context 共用 MySQL 时只发生一次发送。
- 使用 MySQL 8.0.36、RocketMQ 5.5.0 和独立 JVM 故障夹具执行 `mvn clean verify`：全仓 114 个测试，0 失败、0 错误、0 跳过。

## 当前边界

- Context 关闭时停止新扫描与抢占并取消排队任务，但尚无等待在途发送完成的时限和 Producer 关闭顺序保证；完整优雅停机属于 M4.4。
- 租约没有续期；发送持续超过租约时，仍依赖过期恢复和至少一次投递语义。
- `DEAD` 人工重放、Micrometer 指标、结构化生产日志、消费者幂等和真实生产集群故障演练仍未实现。
- 自动调度不保证消息顺序或硬实时送达；下游必须按稳定事件 ID 或业务 Key 去重。

## 下一步

进入 M4.4：停止接受新候选后，在有明确上限的时间内等待在途发送，再按确定顺序关闭 Producer 与执行资源；覆盖正常退出、超时和异常退出场景。
